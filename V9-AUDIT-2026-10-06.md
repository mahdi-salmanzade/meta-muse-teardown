# Muse v9 audit — 6 October 2026

[Reports](README.md) · [Independent review](TODAYS-CHANGES-AUDIT-2026-10-06.md) · [Evidence index](EVIDENCE.md) · [Independent checks](evidence-updates/2026-10-06/11-independent-verification.json) · [Original finding ledger](evidence-updates/2026-10-06/10-v9-audit-findings.json)

**The clearest changes are narrower Mac/Android access surfaces and additional audio code in the iOS sample.** macOS 6.0 removes the bundled Chrome extension and `stealth.min.js`; Android 9.0.0.23.178 removes four media permissions and its agent photo handlers; the third-party decrypted iOS 9.1.0 sample adds Alo live-voice and wearable-recording paths. These are comparisons of saved packages, not a claim that they are the newest releases in every region or account rollout.

This report was corrected after an independent review of commit `3058622`. The original ledger is preserved for traceability; its categorical labels and reviewer votes are not independent proof. Directly reproduced checks are in [11-independent-verification.json](evidence-updates/2026-10-06/11-independent-verification.json). Other findings below remain attributed static analyses from the original ledger. No native Muse app was launched or production account used, and no native traffic was captured.

**Consent can prevent access.** Approving a command does not establish that it completed or transmitted data. The code contains cloud-agent upload paths and persistent sync options; actual results depend on OS permissions, app settings, approval policy, available records and server configuration. The author's “spyware by design” label is an editorial privacy assessment, not a demonstrated finding of malicious intent, covert collection, inevitable upload or an OS-permission bypass.

**8 October follow-ups:** [Alo/Mango/wearable](ALO-AND-MULTIMANGO-2026-10-08.md) and [payment/VM trust](PAYMENT-AND-TRANSPARENCY-2026-10-08.md) extend this analysis without adding new app versions. The [platform guides](VERSIONS.md) give the current interpretation.

## macOS 6.0

### Verified changes

- The bundled `Resources/chrome/` directory and `Resources/stealth.min.js` are absent, whereas both were present in 4.1. Prior browser-extension tests apply to the older bundled extension, not to a component shipped in 6.0. Removed CDP/loopback strings belonged to the native bridge; calling them the extension's own loopback channel was incorrect. Removal alone does not prove that the older path was unreachable.
- Exactly one entitlement was added: `com.apple.security.personal-information.location = true`. Location usage descriptions and CoreLocation references already existed. The app is not App Sandbox-enabled, so the extra entitlement alone does not establish newly granted location access or a TCC bypass.
- All four compared helpers remain identical outside UUID and signature regions. Sparkle is still **2.7.0-beta.1, build 2040**; no `.xpc` service bundles were found.
- Native startup disassembly calls `setAutomaticallyChecksForUpdates:` and `setAutomaticallyDownloadsUpdates:` with **true**. Absence of `SUEnableAutomaticChecks` in Info.plist does not negate those calls. This establishes the startup configuration, not successful installation, an unchangeable policy or exploitability.

### Static findings retained from the ledger

- **Computer control:** ScreenCaptureKit/`SCStream` references and finer key, mouse and window primitives were added. The reviewed paths support desktop observation/input automation and shell commands, with OS permission checks, app approval logic and server flags. They do not establish unrestricted access to every protected surface. The ledger identifies native browser-window automation; actual use on each listed browser was not exercised.
- **Approval weaknesses:** persistent “Always allow” choices, server-governed policy and model instructions about previewing actions merit testing. Prompt instructions to confirm sends, purchases or deletions are not themselves proof of hard enforcement. Runtime behavior of every approval mode was not independently established.
- **Auto-sync controls:** Calendar, Reminders and Contacts have per-connector switch UI and native bridge references. The web dialog uses the supplied `autoSync.enabled` value; its `?? true` fallback is **not proof that all connectors default on**. If no row exists, `Wi?.onChange(Ki)` does nothing. Native disassembly also contains stored-state/configuration branches. The UI describes sync as paused when read permission is Ask/Deny or OS access is missing; runtime enforcement remains untested.
- **Diagnostics and training:** the ledger identifies new `reliability_event_log_upload`, MetricKit and `HatchAppleDiagnostics` references, alongside existing Crashpad and identity-bearing analytics. The web client telemetry setting uses a local default-on expression. That does not establish all native telemetry defaults. `trainingEnabled ?? true` is a **display fallback while query data is absent**, not evidence of the production account default or training use of a record. The ledger also reports new confidential-VM telemetry suppression branches; their runtime coverage is untested.

The pinned update-feed key and signed artifact mitigate feed-tampering scenarios. Sparkle's maintainer describes local-attack preconditions involving specific services or elevated Autoupdate/package-install behavior. The old version warrants follow-up, but an exploitable Muse vulnerability was not reproduced. [Maintainer's advisory and preconditions](https://github.com/sparkle-project/Sparkle/discussions/2764).

## Android 9.0.0.23.178

### Verified changes

- Declared permissions decrease **65 → 61**. Removed: `ACCESS_MEDIA_LOCATION`, `READ_EXTERNAL_STORAGE`, `READ_MEDIA_IMAGES`, `READ_MEDIA_VISUAL_USER_SELECTED`. No permissions were added.
- Photo-handler package descriptors present in the previous DEX files are absent in this sample. The original ledger traces removal of the three `photos.*` registrations and associated upload/label-scanning code. A flag alone cannot restore those removed handlers. This does not establish the absence of all photo attachment, camera or alternative media paths.
- **36/36 native libraries are byte-identical** to the prior sample. The ledger's DEX-host comparison found no added host in its extracted set; unchanged host strings do not prove unchanged traffic, request content or routing.

The 27 September report's 65-permission count remains accurate for the build it inspected. It is superseded for this sample, not retroactively false. The earlier [Android photo section](reports/ANDROID-8.0-9.0.0.11.md#6-photos) describes the older package.

### Privacy findings and qualifications

- **Location/geofencing lack the node approval mapping used by other sensitive sources.** The ledger traces `location.get` and geofence commands past the null node-HITL spec, leaving OS location authorization as a key gate. This concerns an app-level confirmation gap, not an OS permission bypass. Other sources can also run without a new prompt when saved policy allows them.
- **App-open network/battery publishing is wired without a per-action approval spec.** The reviewed sources use AppOpen/TRANSIENT publishing. However, the network helper explicitly clears **SSID and BSSID without `ACCESS_FINE_LOCATION`**, and filters unknown/scrubbed values. It is incorrect to describe those identifiers as always exposed under only the normal network-state permission. No dedicated disclosure/control was found in the searched bundled copy; server-fetched disclosure and actual transmission remain unverified.
- **A cached server baseline can allow unset reads.** `PermissionDefaultMode.fromWire(null/unknown)` falls back to AUTO_ALLOW, and the defaults store writes that normalized value. The ledger traces this to read approval resolution after settings are cached. Missing cache/fetch failure can fall back to ALWAYS_ASK; a cached ALWAYS_ASK policy and explicit user decisions still matter. The actual production response and fresh-install experience were not tested.
- **Historical backfill is broader than a connection-date-only model.** The reviewed time-series parsers require a start date but show no clamp to the connection time; Contacts can enumerate the accessible address book. Calendar and Contacts copy disclose existing information, so a blanket claim of undisclosed history access is unsupported. Messages, Call Log and Health wording deserves closer UX testing. OS permissions and available history still bound results; Health Connect imposes its own history-access rules. [Android history restrictions](https://developer.android.com/health-and-fitness/health-connect/read-data).
- **Notification scope defaults to ALL in app settings.** The listener/filter/publish path and approval checks remain. ALL is an application selection default, not proof every notification field is delivered: platform redaction, profile/device policy and filters can restrict content.
- **Persistence and identity:** the ledger traces boot/update restoration of previously configured geofences, alarms, reminders and sync, with permission rechecks. It also reports caller-UID checks on `FoaPhoneIdProvider`, a disabled radio-signal provider and server-gated advertising/attribution code. These are static findings; the identity allowlist and runtime transmission were not independently reconstructed here.

## iOS 9.1.0 — decrypted sample

All code-path conclusions in this section inherit the decrypted-code limitation above. OS prompts, voice-mode entry, pairing and node approval are different gates; it is inaccurate to claim every path necessarily traverses the same node-HITL check.

### Supported changes

- **New Alo voice path:** the main binary adds `wss://shortwave.facebook.com/vllm_proxy`, `input_audio_buffer.append` and Alo persona text. The ledger traces microphone streaming with voice-mode/session controls and an OS mic prompt. The “always on” phrase is persona copy, not demonstrated continuous capture. The earlier `…/voyager/v1/asr/duplex` socket already existed in 8.1, so off-device audio as a whole is not new.
- **New wearable-recording code:** `HCHDeviceBLEManager`, `HCHMicroRecordingUploader` and “Muse Gadget” appear in 9.1 and are absent in the compared 8.1 binary. The ledger traces pairing/Wi-Fi provisioning, recording upload through Noise/DGW, a consent screen and an owner-mismatch rejection. This supports a code capability, not confirmed shipping hardware, ambient recording or observed upload.
- **Framework correction:** direct Mach-O load-command comparison adds **CoreML.framework and libswiftCallKit.dylib**, and removes **PDFKit.framework and Symbols.framework**. CoreBluetooth, CallKit, Speech, CryptoKit and Vision were already linked. New imported APIs are not the same as newly linked frameworks.
- **Alo model-defaults URL:** `https://www.multimango.com/api/alo/default-models` appears in 9.1. The ledger associates it with a conditional model-defaults fetch and MobileConfig fallback. Ownership remains **unverified**; a hostname outside the familiar Meta domains is not proof of a non-Meta owner. The new role is a lead for the previously unexplained Mac hostname, not proof the Mac path has the same purpose. No user-content upload to it was observed.
- **Notes and telemetry deltas:** `NotesSyncSource` and “Apple Notes” literals disappear from the compared main binary, supporting removal of that identifiable export implementation. This does not rule out every alternative Notes/Shortcut path. The ledger records removal of selected loom/QPL/memory-trace references; it does not establish removal of all telemetry.
- **Other additions reported by the ledger:** cloud-VM/orchestrator and commerce plumbing, call-observer use, a lock-screen avatar widget and `NSPhotoLibraryAddUsageDescription`. Cloud browser screen operations and operator SSH references concern the VM, not established remote control of the phone's OS.

### Continuing concerns and limits

- Selected collection-command **names** remain present (`photo.sync`, location/geofence, Health, Home, Calendar, Contacts, forwarding and backfill). A literal-name comparison does **not** establish a byte-identical dispatch table or unchanged implementation. The ledger identifies `voice.audioroute` as an added token within its selected namespace search, not an exhaustive proof that no new device action exists.
- `photo.sync` copy describes a persistent full-library override; the 9.1 setter was not independently re-derived in the ledger. Photos authorization still matters. `processing` remains absent from background modes, so a task identifier alone does not prove periodic BGProcessing execution. [Apple's processing requirement](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask).
- **110 distinct HealthKit type-identifier imports** are present, together with background-delivery/raw-sample-sync indicators reported in the ledger. Imports do not prove reads, granted types, immediate scheduling or uploads. Those behavioral inferences cannot be authenticated merely because the import list resides outside the encrypted region.
- Significant-change location requires relevant OS authorization. iMessage/Mail forwarding is described through user-created, revocable Shortcuts; a historical Messages database reader was not established.
- Shared app-group/keychain entitlements permit access among appropriately entitled peers, but do not prove a particular cross-app exchange or its disclosure status. Operator-SSH and silent-push references similarly do not establish live operator access or an approval bypass.
- Background modes remain `audio`, `fetch`, `location`, `remote-notification`; **`bluetooth-central` is absent**. This limits ordinary central-role background handling, but is not proof that the app can never run in the background through any mechanism. [Apple's Bluetooth background rules](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html).

The older iOS report already distinguished absence of an **agent microphone command** from user-initiated mic capture. It should not be “corrected” as if it had claimed that all microphone paths were absent. The 110-import count was also already recorded in the earlier evidence.

The verifier expects the saved packages in `muse-v9/`, the October extractions in `extracted/v9/` and the prior baseline in `extracted/release-audit-2026-09-27/`. None of the target app code is executed. It reuses the earlier CMS/page/resource verifier and adds current signature, permission, framework, token, helper and bounded source/disassembly checks. It is a targeted review, not a complete reconstruction of every native instruction.

Still open: production defaults and server policy; fresh-install/denial behavior; native upload content; retention/deletion/training treatment; wearable availability and ownership enforcement; and authenticated retail iOS code.
