# Muse v9 audit — 6 October 2026

[Reports](README.md) · [Spyware verdict (v8)](SPYWARE-VERDICT-2026-09-27.md) · [Cross-platform](CROSS-PLATFORM.md) · [Evidence index](EVIDENCE.md) · [Findings data](evidence-updates/2026-10-06/10-v9-audit-findings.json)

A new Muse wave landed: **macOS 6.0**, **Android 9.0.0.23.178**, **iOS 9.1.0**. Each platform was analysed independently — its own finders, its own adversarial verification, its own verdict — against the documented prior build. This page keeps them separate. The method is static only: no Muse app was launched, no binary or script executed, no Meta host contacted.

**The thesis is unchanged and, on iOS, strengthened.** Muse still asks permission, and the permission still decides *when* your data goes to Meta, not *whether*. The agent runs in a Meta-hosted VM, so every read it performs and everything it keeps in sync is copied to Meta by design. v9 moves in two directions at once: **macOS and Android trim surface** (Mac drops the bundled Chrome extension and its anti-bot-detection kit; Android removes the whole agent photo subsystem and four media permissions), while **iOS adds new off-device audio channels to Meta** — live microphone voice and a Bluetooth audio wearable.

Across all three: **no covert channel, no hidden payload, no code injection.** All three samples are authentic (Mac signed+notarized with a valid update-feed signature; Android v3 + Google source stamp, signer unchanged; iOS CMS-verifies to Apple's root). The label "spyware by design" remains an assessment about breadth of consented collection into Meta, not a claim of hidden exfiltration.

## macOS 6.0 — independent verdict

**Consent-gated surveillance-grade collection with named weaknesses; covert surface reduced vs 4.1.** Of nine findings put to two adversarial lenses, none were refuted.

### What changed from 4.1

**Removed (surface reduced):**
- The entire bundled Manifest-V3 Chrome extension (`Resources/chrome/`, 10+ files) and **`Resources/stealth.min.js`** (the 180 KB puppeteer-extra anti-bot-detection kit) — both confirmed absent in 6.0, present in 4.1. The native CDP bridge strings (`cdpError`, `webSocketDebuggerUrl`, `.hatch-extension-stamp`, `Library/Application Support/Hatch/ChromeExtension`) are gone, and the extension's `127.0.0.1` CDP loopback is the only removed host.

**Added / expanded:**
- **ScreenCaptureKit** is the new screen-capture backend (`SCStream` imports; 0 occurrences in 4.1), replacing the older AVCapture path. Finer synthetic-input primitives were added (`hold_key`, `release_key`, `left_mouse_down/up`, `set_window_frame`).
- **One new entitlement** — `com.apple.security.personal-information.location = true` — the only entitlement change. Note: the `NSLocation…UsageDescription` strings and the CoreLocation symbols already existed in 4.1, so this flips a bit on a capability that was already reachable; the wired mechanism is foreground `startUpdatingLocation` feeding the in-app map, not background geofencing (`startMonitoringSignificantLocationChanges` / `requestAlwaysAuthorization` are absent in both builds).
- **Expanded diagnostics:** a new `reliability_event_log_upload` endpoint, Apple **MetricKit** subscription, and `HatchAppleDiagnostics` — none present in 4.1.
- **New agent-permission disclosure rows:** "the assistant driving a web browser on the user's behalf" and "the assistant running shell/terminal commands on the user's computer".

**Unchanged:** Sparkle 2.7.0-beta.1 build 2040 (same pre-hardening build), the EdDSA-pinned `facebook.com/endo` feed, the crash URL, the analytics identity schema, and all four helper binaries (byte-identical to 4.1 outside their UUID and signature regions). No LaunchAgent, daemon or XPC service. No new off-Meta endpoint.

### Surviving findings
- **Full-desktop computer-use agent**, expanded in 6.0: observe (Accessibility), control (synthetic input), screenshot (ScreenCaptureKit), across any app, plus shell execution (`system.run`). Gated by TCC (Accessibility + Screen Recording), server flags, and per-action approval, with send/pay/delete forced last. Weaknesses: "Always allow" never expires; the preview is a soft gate (input is posted in the background and never foregrounds apps, so visibility depends on the model honouring a "tell the user" instruction); capability flags are server-flippable. `[REMOTE_CONTROL · GATED · WEAKNESS]`
- **Browser control is native "agent window" automation** of the user's installed browser (Chrome/Edge/Brave/Firefox/Arc/Vivaldi/Opera/Zen/…), gated by the same TCC + approval. This was already the active path in 4.1; 6.0 only deleted the dead CDP/extension files. `[REMOTE_CONTROL · GATED]`
- **Proactive-sync default is server-governed and defaults on** (`endo_rollout:featured_app_proactive_sync_enabled`; client fallback `autoSync.enabled ?? true`). `[CONSENT_BYPASS · GATED · WEAKNESS]`
- **Crash + telemetry carry identity and expanded in 6.0:** Crashpad uploads to `facebook.com/mobile/ios_breakpad_crash_logs/`; `analytics_events` carry `user_identity`/`session_id`; client telemetry defaults on; AI-training preference defaults on (`trainingEnabled ?? true`). New reliability + MetricKit + Apple-diagnostics channels. `[UNDISCLOSED · CONSENT_BYPASS]`
- **Auto-update via the pre-hardening Sparkle beta**, EdDSA-pinned feed, server force-upgrade flag. `[PERSISTENCE · WEAKNESS · GATED]`

### Corrections to prior reports (macOS)
- **"Calendar/Reminders/Contacts have no in-app auto-sync switch" is now FALSE for 6.0** — native per-connector switches were added with disclosure copy ("New and changed contacts are shared automatically. Turn this off to share only what you ask for."). The residual concern is the pre-checked, server-set default, not the absence of a control.
- **README §6/§7** (Chrome-extension debugger access; `stealth.min.js` bot-evasion) **no longer describe 6.0** — both were deleted.
- The crash handler is **Google Crashpad**, not Breakpad (only the legacy URL token keeps the name). `reliability_event_log_upload` is new in 6.0. "Auto-update forced on" is not statically provable (no `SUEnableAutomaticChecks`; a permission-prompt delegate exists).

## Android 9.0.0.23.178 — independent verdict

**Consent-gated surveillance-grade collection with named weaknesses; a net reduction in collection surface vs 9.0.0.11.** No covert channel at the container, native-library, or network level.

### What changed from 9.0.0.11.178
- **Four permissions removed, none added (65 → 61):** `ACCESS_MEDIA_LOCATION`, `READ_EXTERNAL_STORAGE` (maxSdk 32), `READ_MEDIA_IMAGES`, `READ_MEDIA_VISUAL_USER_SELECTED`.
- **The entire agent photo subsystem was deleted** — `com/facebook/aura/commands/photos/` went from 52 files to 0 (PhotosUploadHandler, PhotoUploadWorker, DeviceMediaStoreReader, PhotoLabelScanner, …). The `photos.*` commands are unregistered (42 → 39 handlers); a request now returns UNKNOWN_COMMAND. Re-enabling would need an app update, not a server flag — the `is_nodes_media_enabled` flag is now inert.
- **On-device ML Kit image labelling removed** (vision registrars/service and the MLKit version-pins are gone).
- **Unchanged:** 36/36 native `.so` byte-identical to the prior build; the DEX endpoint host set byte-identical; 12 data sources, all other commands, gates and exported components structurally identical. The "new realtime hosts" a finder first flagged were a decompiler artefact (present in both builds).

### Surviving findings
- **`location.get` and geofence commands carry no in-app approval card** — gated only by the OS location permission, unlike every other sensitive source, which prompts. `[CONSENT_BYPASS · WEAKNESS]` (severity high)
- **`network_state` (SSID/BSSID) and `battery` publish on every app-open** with no HITL, no toggle, no in-app disclosure (low-sensitivity payload; retention not shown). `[CONSENT_BYPASS · WEAKNESS]`
- **A server-held baseline can resolve reads to auto-allow.** `PermissionDefaultMode.fromWire(null/unknown) → AUTO_ALLOW`, and the defaults store persists an omitted `connector_default` as `auto_allow`, so after the first settings fetch an unset READ of SMS/call-log/contacts/calendar/notifications can publish with no prompt. The fail-closed-to-ASK behaviour applies only before any settings are cached. `[CONSENT_BYPASS · WEAKNESS]`
- **Backfill has no connection-date floor.** The four time-series sources require a `start_date` but accept an arbitrarily early one; contacts sweeps the full address book. Consent copy says "shared after you connect". `[GATED · WEAKNESS]`
- **Notification listener ingests all apps by default** once access is granted (`PhoneNotificationsAccessMode = ALL`), wired to publish. `[UNDISCLOSED · GATED]`
- **Exported boot receiver re-arms** geofences/alarms/reminders/sync and re-binds the listener across updates — but only previously-consented state, re-checking live permission. `[PERSISTENCE]`
- `FoaPhoneIdProvider` is exported but caller-UID-gated; `libtrafficnts.so` radio-signal provider is **hardcoded off**; GAID/attribution is retained and server-gated. `[GATED]`

### Corrections to prior reports (Android)
- **`RELEASE-AUDIT-2026-09-27.md §3` "all 65 declared permissions unchanged" is now wrong** — 61 permissions; the four media/photo perms were removed.
- **Prior finding "photos.upload behind `is_nodes_media_enabled`, default off" → downgrade to REMOVED** for this build: the handlers are gone, not merely flagged off.
- **`ANDROID.md §6` (Photos) is stale** — agent photo read/upload and on-device image labelling are no longer present capabilities. The only remaining photo path is the permissionless, user-selected system Photo Picker.
- The "backfill no lower date bound" shorthand should read "no clamp to connection time / no minimum floor; contacts = full address book" (SMS/call-log/calendar/health require a non-null `start_date`; notifications is not backfillable).

## iOS 9.1.0 — independent verdict

**Consent-gated surveillance-grade collection with named weaknesses — unchanged in character, broadened by new off-device audio channels to Meta.** No covert channel found; every collection path is permission-gated, node-HITL-gated and disclosed in tool text. Caveat: this is a third-party decrypted IPA, so the decrypted code bytes cannot be checked against Apple's signature (the HealthKit evidence is the exception — it lives in `__LINKEDIT`, which is never encrypted).

### What changed from 8.1
- **Live voice to Meta (the biggest delta).** A new "Alo" speech-to-speech agent — *"You are Alo, a personalized AI assistant that is always on built by Meta AI."* — streams microphone audio over a new WebSocket `wss://shortwave.facebook.com/vllm_proxy` carrying `input_audio_buffer.append` frames. (Every one of these tokens is 0 in the 8.1 binary.) New frameworks linked: CryptoKit, CoreBluetooth with state restoration, CallKit, Speech, CoreML, Vision. *Correction to the finders: the `…/voyager/v1/asr/duplex` ASR socket is not new — it is present in both 8.1 and 9.1; only `vllm_proxy` is new.*
- **A Bluetooth audio wearable pipeline** — `HCHDeviceBLEManager` / `HCHMicroRecordingUploader` / "Muse Gadget" (all 0 in 8.1): pairs a Meta audio wearable, provisions Wi-Fi over BLE, pulls stored audio recordings and uploads them "over the Noise gateway transport", behind a per-recording fail-closed owner check ("owner does not match session user"). The Noise/DGW transport itself pre-existed in 8.1; only the BLE + uploader layer is new. No `bluetooth-central` background mode, so iOS cannot background-relaunch the app for the device.
- **A non-Meta host, now explained.** `https://www.multimango.com/api/alo/default-models` (hardcoded, 0 in 8.1) — the Alo model-defaults fetch, used only when a token/URL is provisioned, else falling back to a Meta MobileConfig tier. This resolves a prior open item: CROSS-PLATFORM.md already listed `www.multimango.com` as an unexplained macOS domain; it is the Alo model-defaults endpoint.
- **New orchestrator / cloud-VM surface:** hosts `vm.meta.ai`, `vm.muse.ai`; an "Always-on, server-side text-only orchestrator … subagents, sandboxed code execution, and a wide tool set"; scheduled-task plumbing. The "screen operations" act on the cloud VM's browser, not the phone.
- **Agentic-commerce server plumbing** (`odyssey_server_driven_prepare_purchase`, `payments-graph.facebook.com`, PayPal/escalation routing). The on-device checkout approval sheet already existed in 8.1.
- **Removed:** Apple Notes full-text export (`NotesSyncSource` and all "Apple Notes" strings → 0); PDFKit; the loom/QPL/memory-trace telemetry stack (~181 flags).
- **Add-only:** `NSPhotoLibraryAddUsageDescription` (save-to-library), a CallKit call observer (audio ducking), a lock-screen avatar widget.
- **Unchanged — the collection core.** The node data-collection command table is byte-identical 8.1→9.1 with identical counts (`photo.sync`, `location.*`, `geofence.*`, `health.samples`, `home.*`, `calendar.*`, `contacts.*`, message forwarding, backfill). The only new command-namespace token is `voice.audioroute`. No new on-device data-pull command was added.

### Surviving findings
- **Alo live voice** streams mic audio to `shortwave.facebook.com`. Gated by voice-mode entry + the OS mic prompt + session-scoped recording with an in-app "Delete all voice activity?" control. `[GATED]` ("always-on" is persona-prompt copy, not proven continuous capture.)
- **BLE wearable audio** uploaded to the Meta VM, behind pairing + a consent screen + the per-recording owner check. `[UNDISCLOSED · GATED]`
- **`photo.sync`** arms ongoing camera-roll sync with a persistent full-library override ("stays on until the user disables it in settings"), behind the Photos permission and an approval card. `[CONSENT_BYPASS · GATED]`
- **HealthKit: 110 type identifiers** with immediate background delivery and raw-sample upload (confirmed by both lenses; evidence in `__LINKEDIT`). `[CONSENT_BYPASS · UNDISCLOSED]`
- **Background location** (significant-change) only after "Always" is granted — hard OS gate. `[GATED]`
- **iMessage/Mail forwarding App Intents** run while locked, but only via a user-built, default-off, revocable Shortcut; no message-history read. `[GATED · WEAKNESS]`
- **Meta operator SSH into the cloud VM** (`ssh.operator.updated`, `/v1/ssh/operator/*`) and a VM-locked silent-push wake — applies to the VM, not the phone; dispatched commands pass the node HITL gate. `[REMOTE_CONTROL · GATED]`
- **Meta-family shared app groups + keychain** (`group.com.facebook.hatch/.family`, `group.com.metaplatforms.family`) enable undisclosed cross-app exchange with same-team Meta apps. `[UNDISCLOSED · GATED]`
- `www.multimango.com` non-Meta host (model-defaults GET; no user content proven). `[UNDISCLOSED · WEAKNESS]`

### Corrections to prior reports (iOS)
- **Apple Notes export is removed** in 9.1 (prior IOS81-10 no longer matches; static removal is not proof of server-side removal).
- **"No microphone capture path" was already wrong for 8.1** (it linked Speech.framework and declared a mic usage string). What is genuinely new in 9.1 is the off-device live-audio channel to Meta.
- Several 8.1 `CONSENT_BYPASS` tags corrected to `GATED` after review found hard OS gates (background location; iMessage/Mail forwarding).
- `multimango.com` is **not** the "first non-Meta endpoint in any report" — it was already logged (unexplained) for macOS; 9.1 explains it.
- HealthKit distinct-identifier count is **110**, not 109.

## What static analysis still cannot settle (all platforms)

- **Live/default values of the server flags** that govern the gates (Mac `featured_app_proactive_sync_enabled` and the computer-control flags; Android `connector_default`; iOS `node_hitl_enabled`, `camera_roll_sync_enabled`, `voice_entrypoint_enabled`). The gates and client defaults are visible; the production booleans are not.
- **Actual transmission.** Every off-device channel — Mac telemetry/crash, Android proactive sync, iOS voice/wearable/health/camera-roll — reaches *present*/*reachable* in code; none was observed on the wire (static-only, by rule).
- **Runtime enforcement of the approval model**, and whether a fresh install ever runs a read with no prompt.
- **iOS code authenticity**: the decrypted IPA's `__TEXT` cannot be checked against the signature, so iOS code-behaviour claims are capability/reachability, not proof the shipped Meta build contains those exact bytes.

These remain the job of the pending dynamic phase (throwaway account + captured traffic) in [RESEARCH-PLAN.md](RESEARCH-PLAN.md).
