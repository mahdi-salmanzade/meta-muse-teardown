0. VERDICT (summary)
--------------------------------------------------------------------------------
PARTIALLY CONFIRMED mechanism swap; REFUTED as to "private" and "no longer
publicly auditable". Overall: NEEDS-REQUALIFICATION.

* The Sigstore/Rekor verifier really was deleted from Android/iOS in the v9
  wave, with an explicit replacement error string: "Sigstore transparency
  proofs are no longer supported". Cloudflare Plexi-signed proofs are the sole
  supported transparency mechanism in v9.
* BUT Plexi was NOT added in v9: the complete Plexi verifier and Cloudflare's
  pinned auditor keys already exist in Android 8.0, iOS 8.1, and macOS 4.1.
  v8 supported BOTH proof types, policy-selectable. v9 removed one of two.
* "Private" is wrong: Plexi is Cloudflare's OPEN-SOURCE auditor
  (github.com/cloudflare/plexi). The app pins Cloudflare's PUBLICLY ADVERTISED
  auditor keys, and the exact transparency namespaces the app consumes
  (prod.hatch_image, prod.pc.revocation_list) are listed and queryable on
  Cloudflare's public auditor endpoint. A live audit signature for
  prod.pc.revocation_list epoch 1 was fetched and cryptographically verified
  against the public key that is byte-identical to the app's pinned key.
* The old Rekor path was itself not clearly "public": the only pinned Rekor
  endpoints in v8 are rekor.sigstage.dev (Sigstore STAGING, explicitly
  non-production). rekor.sigstore.dev (the public instance) appears nowhere.
* Real residual concerns (the defensible core of the claim): the v9 client
  verifies ONLY the auditor's Ed25519 signature over (namespace, epoch,
  digest) -- it no longer verifies a Merkle inclusion proof itself -- and the
  hatch CVM namespaces expose no public log_directory, so third parties can
  verify auditor signatures but cannot enumerate what was logged. Meta itself
  admitted (engineering.fb.com, 2026-03-09) that artifacts for external
  researcher validation are not yet released ("We aim to provide a platform
  for hosting these artifacts in the near future").

2. WHAT v8 ACTUALLY CONTAINED (Q1: was Rekor wired into production attestation?)
--------------------------------------------------------------------------------
v8 (Android 8.0 libstartup.so; iOS 8.1 HatchApp) contained BOTH verifiers in
Meta's own attestation verifier (Rust, xplat hatch/noise + TigonNoise):

a) The bulk of the 155 "sigstore" strings are VENDORED library text:
   sigstore-go / sigstore protobuf-specs ("Copyright 2022/2025/2026 The
   Sigstore Authors", bundle-spec prose, "application/vnd.dev.sigstore.*"
   media types, dev.sigstore.proto.* type URLs, github.com/sigstore/*
   doc URLs, TransparencyLogEntry/TrustedRoot proto descriptors).

b) But the Sigstore path is NOT dead vendor code. It is glued into Meta's
   attestation pipeline with Meta-specific policy/verification strings:
   - "policy requires a transparency proof"
   - "policy does not accept Sigstore transparency proofs"
   - "policy does not accept Cloudflare transparency proofs"
   - "no pinned Rekor key for logId "
   - "manifest signer key is not pinned for this environment"
   - "rekor entry signature does not match the artifact signature"
   - "rekor entry digest does not match the signed digest"
   - "Fulcio leaf key does not match the key logged in Rekor"
   - "no Fulcio CA anchors pinned"
   - Rekor inclusion-proof verification structs (single string table):
     "...TransparencyProof proof InclusionProof tree_size hashes checkpoint
      root_hash LogId ... checkpoint missing tree size / root hash / origin /
      missing blank-line separator before signatures ... tlog entry missing
      inclusionProof / logId ... rekor body missing data/signature/verifier..."
   - The attestation envelope: "AttestationBundle image_manifest
     transparency_proof report_data_input" with the SAME
     "ImageManifest{vm_sha256, launch_digest, schema_version, commit_sha,
     image_version}" the v9 Cloudflare path uses, and namespaces
     "prod.hatch_image" / "staging.hatch_image".
   => The Rekor verifier checked inclusion of the hatch image manifest in a
      Rekor log, verified checkpoints (note-format), and matched the Rekor
      entry against the artifact digest/signature. That is production-shaped
      wiring, gated by policy ("policy does not accept ..." implies a policy
      chooses accepted proof types).

c) CRITICAL QUALIFICATION: the only Rekor endpoints embedded are Sigstore
   STAGING:
     https://rekor.sigstage.dev
     https://log2025-alpha1.rekor.sigstage.dev
     https://log2025-alpha2.rekor.sigstage.dev
     https://log2025-alpha3.rekor.sigstage.dev
     https://log2026-1.us-east4.rekor.sigstage.dev
   "rekor.sigstore.dev" (the public-good instance): 0 occurrences in both v8
   binaries. So even in v8, "public transparency log" meant Sigstore's
   explicitly non-production staging infrastructure (or a server-delivered
   TrustedRoot config; static analysis cannot resolve which).
   (CROSS-PLATFORM.md:126 had already flagged the sigstage pinning.)

d) UNKNOWN (unresolvable statically): whether production v8 servers ever
   actually served Sigstore-type proofs, or whether the deployed policy was
   already Cloudflare-only in practice. The presence of "policy does not
   accept Sigstore transparency proofs" as an error branch is consistent with

--------------------------------------------------------------------------------
* Main binary Muse (4.1 AND 6.0): 0 sigstore/rekor/plexi/sigsum strings; the

  Contents/Resources/hatch/index.html. In BOTH 4.1 and 6.0 it is already

  were never accepted on macOS). 6.0 adds a "debug" attestation tier

  pinned in both. 4.1's two "rekor" hits are Polish/Hungarian "rekord"

Residual, real limitations of the new system's public auditability:
  - The hatch/pc CVM namespaces have log_directory = null/"" (unlike
    messenger.key-transparency.v1, which publishes a CloudFront log
    directory). So the public can verify that Cloudflare signed
    (namespace, epoch, digest) statements, but cannot enumerate the log's
    entries (which image digests were logged when) or recompute the tree.
  - prod.hatch_image is still "Initialization" (consistent with Muse CVM
    being announced but not GA) -- no hatch image epochs to audit yet.
  - The v9 CLIENT performs no inclusion-proof verification itself; it trusts
    the auditor. v8's Rekor path let the client verify inclusion directly
    (albeit against sigstage). This is a genuine trust-model downgrade on
    the client side even though the auditor side is public.
