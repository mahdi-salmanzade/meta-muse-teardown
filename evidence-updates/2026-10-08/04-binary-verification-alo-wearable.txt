Corrections to the original ledger:
- 0x3cb6820 is the dispatch-queue label com.meta.hatch.alo.ws, not part of the
  append/URL strings (labeling only).
- 8.1 DOES contain shortwave.facebook.com (1x) for dictation endpoints
  /voyager/v1/asr/duplex and /v2/transcription. The /vllm_proxy path and all
  Alo machinery are 9.1-only.
- "base64 PCM" is protocol inference: no local pcm16 format string exists for
  Alo; input_audio_format/output_audio_format keys sit next to the session
  template and base64Encoded call sites exist. Alo output path is Opus
  ("Failed to create Opus encoder for Alo output").

OpenAI-Realtime-style event vocabulary present in the same region:
  input_audio_buffer.speech_started / speech_stopped, response.created,
  response.output_audio.delta, response.output_audio_transcript.delta/done,
  conversation.item.input_audio_transcription.delta/completed,
  response.function_call_arguments.delta/done, interrupt_response,
  semantic_vad_avocado, plus an embedded audio-tokenizer vocab (<|audio_vq_*|>).

Additional material in 0x3cb6000-0x3cb8000 not used by the ledger:
- orchestrator.dispatch tool: "Always-on, server-side text-only orchestrator...
  access to subagents, sandboxed code execution... Dispatch is async /
  fire-and-forget — the orchestrator follows up via a notification."
- Wearable-specific prompt: "You are answering a voice query from a small
  audio-only wearable. Reply with a single short spoken sentence — no visual

- Model-tier logic: "[AloModels] no token/url — using MobileConfig tier",
  "[AloModels] fetched defaults: s2s=", "Using dynamic model tier:" — the
  multimango fetch is a default-models fetch with MobileConfig fallback.

## CLAIM C — gates: CONFIRMED with refinements

1. NSMicrophoneUsageDescription "This allows you to talk to Muse and ask
   questions with your voice." — byte-identical in 8.1 and 9.1. It does not
   disclose wearable recording upload or an "always on" assistant.
   NSBluetoothAlwaysUsageDescription also identical.
2. aloVoiceEnabled: 2x in 9.1, 0x in 8.1 (local settings key).
   voice_entrypoint_enabled: 1x in 9.1, 0x in 8.1, inside a server-pushed
   capability/config schema — the entry point is server-gated.
3. Wearable consent UI exists: "Connect to {device}?", "Confirm by pressing
   the button on your device", plus community-device warning:
   "You are pairing a community device not verified by Meta. It will be able
   to read and send messages, change your files, approve actions, and use
   your browser. This is dangerous." with warning-continue / warning-cancel /
   "Exit to safety" / "Verified Meta device" badge.
   Sync refusal: "Got file list but sync is not allowed" (0x3cb82c0),
   "Sync not allowed: peripheral=". No local token naming what decides
   "sync allowed"; appears driven by session/owner state.
4. "Always on" is persona copy. UIBackgroundModes identical in both versions
   (audio, fetch, location, remote-notification); bluetooth-central ABSENT in
   both, so CBCentralManager state restoration cannot relaunch the app in the
   background. BGTaskSchedulerPermittedIdentifiers unchanged
   (cameraroll.sync, nodedata.sync); com.taskInfo.hatch.micro.recording.upload
   is an internal queue label, not a registered BGTask. No evidence of covert
   continuous capture; the audio background mode + "Keep-alive expired
   (%s idle); ending session" show user-initiated session persistence only.
