1. Model training: default and opt-out
----------------------------------------------------------------------
[L] "People can also opt out of their interactions being used to train Meta's AI models."
[R] "Inference data, the back and forth conversations between you and your Muse and the tool calls and
    subagent handoffs that result ("trajectories") are useful data for training new checkpoints"
[R] "To preserve user privacy, these trajectories are sanitized to remove key personally identifiable
    information before being used in training. We think this is a good default ... If you do not want
    your data to be used in model training at all, you can opt-out via a simple switch in Muse settings."
App:
  all  "Help improve our AI models" / "Allow us to use your interactions with Muse to develop and improve AI at Meta."
       (macOS W@46274026, Android R 0x7f1205aa, iOS B@61120464)
  all  "Your interactions with Muse won’t be used to improve AI at Meta after you turn this off."
  mac  W@46274201 "Hi=r.data?.trainingEnabled??!0"  (ON if the server sends nothing)
  and  J settings/HatchAiTrainingApi.java:24 "DEFAULT_ENABLED = true"; J settings/ProductImprovementsResponseJson.java:78,85 default true
  iOS  default not readable (text only).
AGREES: training is on unless the user opts out; the switch exists on all three platforms.
APP ADDS: the "after you turn this off" wording covers future use only. Neither the app nor [R] says
  whether data already collected, or checkpoints already trained, are removed on opt-out (GAP).
APP ADDS: connector consent footers put connector data inside the training scope:
  Android R 0x7f1206e7 (Health Connect) "All of the info from %1$s is part of your interactions with %4$s,
  which we may use to improve AI at Meta."; iOS B@60850272 "... which we use to improve AI at Meta.";
  macOS W@42158098 "... explains how we use this info, including to improve AI at Meta."
  [R] names "tool calls" as training data but does not mention health data or connector data by name.
GAP: the app never mentions the PII sanitisation that [R] describes.

2. Choice over connections / defaults for sharing
----------------------------------------------------------------------
[L] "People choose which apps Muse connects to and exactly how much access it gets. For things like email,
    people choose what Muse can do, whether it reads their mail or can also send on their behalf."
App:
  mac  auto-sync rows: "New messages are shared automatically. Turn this off to share only what you ask for."
       (W@42164539); Mail: "Who new email is from and what it is about are shared automatically. The message
       text is shared only when you ask." (W@42164742). The consent dialog switch falls back to ON
       (W@42172078 "...useState)(Wi?.autoSync.enabled??!0)") and is committed on Connect (W@42172253).
  and  "Your agent will store existing information from Calendar ..." (R 0x7f1206d0); Contacts same (R 0x7f1206d2).
  iOS  "Turn on to back up your camera roll." (B@61127088) - wording suggests opt-in; in-code default unknown.
AGREES: users pick which connectors to add and read vs read/write levels (macOS "Read only" / "Read and
  interact", W@44792693/44792747).
TENSION: [L] frames access as chosen "exactly", but once a connector is added the app copy describes
  automatic, continuing sharing ("automatically updated with the latest information from your device going
  forward"), and for Calendar/Contacts (Android) and Contacts (macOS) the upload of existing data.
  On macOS the only opt-out inside the consent flow is a switch whose code fallback is ON.
GAP: neither post mentions automatic background sync, historical backfill, or its depth.

3. Asking before acting (approvals)
----------------------------------------------------------------------
[L] "Muse checks with the person before sensitive actions like sending an email or making a purchase."
[L] "Nothing Muse does reaches the internet unless the Sentinel approves it, and it asks the person for
    permission when needed."
[R] "Read-only, previously allowed, or demonstrably low-risk actions can proceed without interruption."
[R] "Muse has support for obtaining one-time, session-scoped, task-scoped, time-bounded, or perpetual permission."
App:
  all  "Connector defaults" - "Ask for some actions" - "Before every write and some read actions";
       "Always ask" - "Before any action"
  mac  internal value of "Ask for some actions" is `auto_allow` (W@44936673) and it is the fallback default
       (W@17154492 "...??`auto_allow`"); Android PermissionSettings.java:102,107 default AUTO_ALLOW.
  mac  "Request was auto-allowed as deemed low risk" (W@17933220); Android/iOS "Auto allowed".
  mac  "These defaults apply when no permission has been saved. “Always allow” choices do not expire." (W@44932832)
  and  READ defaults to ALLOW, WRITE to ASK (J nodes/core/NodeHitlMode.java:28,31).
  and/iOS "By default, your agent will ask before taking actions it thinks need review." (R 0x7f1207a3, B@61364064)
AGREES: writes/sends ask by default; reads and "low-risk" actions may run unprompted; "Always allow" is
  the "perpetual" permission [R] describes.
TENSION (wording only): the default is labelled "Ask for some actions" in the UI but stored as
  `auto_allow`, and it lets background reads of connected sources proceed without a prompt (Android code
  reading; macOS auto-sync copy). [L]'s "checks with the person" is accurate for sends/purchases but does
  not tell readers that reads are not checked.
APP ADDS: macOS says "“Always allow” choices do not expire"; neither post says how perpetual approvals
  are listed or revoked (the app has "Reset approvals to defaults", W@44991335).

4. Disconnecting and what happens to earlier data
----------------------------------------------------------------------
[L] "People can change access or disconnect a service whenever they want."
[R] no sentence on disconnect or connector data retention (extraction tool reported none).
App:
  all  "When you disconnect, Muse will no longer have access to new data from {app}. Previous data shared
       with Muse won't be removed unless you choose to delete it." (W@20718706, R 0x7f1206c4, B@60853104)
  iOS  "Messages already shared are not deleted." (B@60863824); agent tool: "Previously uploaded messages
       are not deleted." (B@61192396)
  all  "You can ask your agent to delete this info at any time, or disconnect from {service} in your device's
       settings to prevent future syncing."
AGREES: disconnect is available at any time.
APP ADDS (material): disconnecting stops new collection only; data already uploaded stays unless the user
  separately asks the agent to delete it. The public posts do not say this.
GAP: no public or in-app statement of how long connector data is kept, or whether "ask the agent to
  delete" also removes backups.

5. Memory and "forget"
----------------------------------------------------------------------
[L] "Muse remembers what matters to a person, and they can always tell it to "forget" specific things it's learned."
[L] "Muse also remembers what matters to a person, so it can make suggestions unprompted."
[R] "You can inspect, edit and download these files freely, including Muse's memory about you."
App:
  and/iOS "You can delete messages you’ve sent. Messages you delete are removed from the conversation but may
       stay in the agent’s memory." (R 0x7f120592, B@61405342)
  all  memory import: "... will read this and remember the durable facts. This is not a verbatim copy."
  mac  "New ideas show up here as Muse learns about you." (W@43659452)
AGREES: memory is persistent and forgetting is an explicit, separate request.
APP ADDS: deleting a chat message does not delete what memory derived from it; [L]'s "forget" sentence
  does not warn about this.
GAP: no statement on whether "forget" removes memory from backups or training data.

----------------------------------------------------------------------
[R] "It restricts access to your data by Meta personnel through operational policies. It does not prevent
    Meta from accessing data when necessary to support, secure or operate the service."
[L] "Later this year, Meta will introduce Muse Confidential VM, where the whole VM, including a person's data
    and conversations with Muse, is encrypted with a key only they hold, so not even Meta can access it."
[L]/[R] no sentence on human review of conversations for training or safety (extraction tool reported none).
App:
  and/iOS "Allowing access means your chats, memory, and files will be visible to support and your data will
       no longer be confidential." (R 0x7f120536, B@61110928); "... Support will access your account to
       investigate and resolve the issue. Access ends when the issue is resolved, or you can revoke it at any time."

       improve {appName}." (B@62514608)

       not to include them." (W@16861405, R 0x7f12012e, B@62514208)

AGREES: support access is user-granted and revocable; the "no longer be confidential" wording fits the

APP ADDS: bug reports include recent conversation details by default and are sent "for review" (iOS).
GAP: no app or public statement says whether people at Meta review conversations, connector data or
  training trajectories. iOS contains "Media human review" setting identifiers from a shared Meta AI
  framework, logged as "no handler linked"; they are not user copy.

SUMMARY
----------------------------------------------------------------------
Agreements: training on by default with an opt-out switch; users pick connectors; approvals include
  one-time and perpetual scopes; reads/low-risk actions can run unprompted; memory is persistent and
  "forget" is explicit; data download exists; support access needs user consent.
Material things the app says that the public posts omit:
  (1) disconnecting does not delete data already shared;
  (2) deleting a message does not remove it from memory;
  (3) connector data, including Health Connect data, is covered by the "improve AI at Meta" language;
  (4) sharing is automatic and continuing after connect (macOS switch falls back to ON), with existing
      Calendar/Contacts data stored on Android and existing Contacts on macOS;
  (5) bug reports include recent conversation details unless the user unticks them.
Unresolved tensions: "permanently deletes" vs continuous backups; "checks with the person" vs a default
  stored as `auto_allow` that lets reads run unprompted.
No contradiction proven: every tension depends on server values or runtime behaviour this static
  review cannot see.
