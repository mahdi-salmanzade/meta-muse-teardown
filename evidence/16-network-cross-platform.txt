Samples: macOS 3.0 (com.meta.endo), iOS 8.1.0 (com.facebook.hatch), Android 8.0.0.21.168 (com.facebook.aura).
Per-platform detail: evidence/16-network-macos.txt, evidence-ios/16-network-ios.txt,
evidence-android/16-network-android.txt. Everything below is derived from those files plus a direct string check.

Method for "shared" hosts and methods: fixed-string search of
  macOS   = strings of Contents/MacOS/Muse + Chrome extension JS + Info.plist, and the web bundle Resources/hatch/index.html
  iOS     = strings of the 5 Mach-O binaries (app, MobileConfig framework, 3 extensions) + Info.plist
  Android = host-like tokens in jadx sources/resources + strings of lib/arm64-v8a/*.so + decoded manifest
A host counts as present when its exact string occurs. Presence proves a reference, not a connection.
Associated-domain entitlements were not part of the iOS search. The iOS IPA failed strict signature
verification (evidence-ios/01), so iOS strings are "present in this sample".

## B. GATEWAY PROTOCOL / RPC MAP (unified)

Supported shape in all three samples: a VM gateway WebSocket, including WSS to
hatch.metaaivm.com/v1/noise or a per-VM URL from the lease response, with Noise_XX_25519_AESGCM_SHA256
support. Endpoint, connection count and selected transport were not observed at runtime. Frames are JSON
{type: req|res|event, id, method|event, params|payload}. Each method string is paired with an HTTP-style
route (/chat/stream, /nodes/register, /client/data-source-publish ...) that the gateway serves over the same
channel. The VM-side agent runtime is called "Jarvis".

Two generations coexist:
  - node.* (older "node" protocol): used by the macOS Chrome extension (node.register / node.invoke.request /
    node.invoke.result / node.heartbeat) and present in the macOS and iOS native method tables.
  - client.* (newer): macOS native and Android Java use client.invoke -> client.invoke.result and
    client.data_source.publish. On Android node.* strings exist only in the shared native library
    (lib:libstartup.so); the Java client does not use them and node.invoke.request is absent.

D->M = device to Meta gateway/VM; M->D = gateway/VM to device.
USER DATA: YES = can carry personal content off the device; cmd = carries the agent's command/params
(which can include user-authored text, e.g. an SMS to send); meta = identifiers/state only (per code).

Reading: the content path (device <-> VM) is designed to be encrypted end-to-end to the VM with Noise and
optionally bound to an attested AMD SEV-SNP "confidential VM". Whether attestation is enforced is decided by
server flags on every platform, and an accept-all verifier class exists. Even when enforced, the VM is run by
Meta, so this limits who can read traffic in transit, not what the agent on the VM does with the data.
An anonymous lease path is identified; broader OHTTP use and actual account/VM
unlinkability are unverified. Shared GraphQL support is described above.

## F. WHAT STATIC ANALYSIS CANNOT DETERMINE
  - Which of these hosts are contacted in practice, and what the payloads of client.invoke.result,
    client.data_source.publish, node.invoke.result, photo sync and chat actually contain (Phase 2 test D3).
  - Server-side flag values that decide whether Noise private auth and SEV-SNP attestation are enforced, whether the
    ACS/OHTTP lease path is used, which GraphQL queries go through OHTTP, telemetry sampling, and the Android
    attribution "compliance action".
  - Meta's native pin sets for meta.ai / metaaivm.com / muse.ai, and whether the whitehat pinning bypass is reachable.
  - Where Chandra / Falco batches land on macOS (hosts built at runtime), and whether Sentry is initialised in the
    macOS web UI.
  - Whether crash minidumps, logcat or debug-log attachments contain user content in practice.
  - Ownership of the non-Meta-looking domains (multimango.com, pariscope.dev, willow606.com, exe.xyz, hatch.one).
  - Server-side retention, linkage and use of anything received.
